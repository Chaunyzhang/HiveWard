A Remote HiveWard Server lets one computer do the work while another computer provides the UI. The server keeps the projects, worktrees, terminals, tabs, provider accounts, and agent sessions. Your laptop connects to that running HiveWard instance.

The easiest setup is the HiveWard desktop app on both computers, connected through [Tailscale](https://tailscale.com/). You do not need to run `hiveward serve` for this path.

<Callout title="Beta">
  Remote HiveWard Servers are beta. Keep the server and client on a private network path you control,
  such as the same Tailscale tailnet or LAN.
</Callout>

## What runs where

```text
Client computer · HiveWard client
  Shows the UI and sends your input
                 │
                 │ private network route
                 ▼
Server computer · HiveWard server
  Stores repos and worktrees
  Runs terminals and agents
```

Install and authenticate Codex, Claude Code, OpenCode, `git`, and any provider CLIs on the **server computer**. A login on your laptop does not automatically carry over to the server.

On a headless `hiveward serve` host, register managed Claude/Codex accounts from the server shell (the remote client disables **Add account**):

```bash
hiveward account add --agent claude
hiveward account add --agent codex
hiveward account list
```

Install or refresh agent skills without a Settings UI:

```bash
hiveward skills install --skill hiveward-cli --skill orchestration
hiveward skills update --all
```

## Recommended: desktop app + Tailscale

You need:

- HiveWard installed and updated on both computers
- Tailscale installed on both computers
- Both computers signed in to the same tailnet
- The server computer awake, online, and running HiveWard

Tailscale gives the server a private address that usually starts with `100.`. HiveWard puts that address first in its connection-address picker.

### 1. Create an access link on the server

On the computer that should keep the sessions running:

1. Open the HiveWard desktop app.
1. Open **Settings → Remote HiveWard Servers**.
1. Under **Advertise this app as a server**, click **New Link**.
1. For **Connection address**, select the Tailscale address. It usually looks like `100.x.y.z`.
1. Click **Generate Access Link**.
1. Copy the link under **Pair another HiveWard client**.

If the Tailscale address is missing, confirm Tailscale is connected and click the refresh button beside **Connection address**.

<Callout title="Keep the access link private">
  The pairing URL grants access to this HiveWard runtime. Treat it like a password and send it only to
  the client you intend to pair.
</Callout>

### 2. Add the server on your laptop

On the computer you want to use as the client:

1. Open **Settings → Remote HiveWard Servers**.
1. Click **Add Server**.
1. Enter a recognizable name, such as `Remote Server`.
1. Paste the access link from the server.
1. Click **Add Server**.
1. If the saved server shows **Disconnected**, click **Connect**.

Adding a server saves it without forcing every new project onto it. Open **Advanced → Default host for new projects** only when you want server-routed projects, terminals, provider checks, and browser or mobile handoff to use that server by default.

## Use the remote server

Once the server shows **Connected**, select it or one of its projects and use HiveWard normally. Terminals, agent processes, files, worktrees, and session state live on the server computer.

When several paired clients share that server, the sidebar filter can offer **Hide other-client workspaces** so this device only lists workspaces it created. See [Worktrees → Sidebar layout](/docs/model/worktrees#sidebar-layout).

That means:

- agents keep running when the client laptop sleeps or disconnects;
- the server needs the repository, tools, and credentials used by those agents;
- the server must stay awake and connected to the tailnet;
- reconnecting the client or reopening HiveWard returns you to the server-owned workspace, tab, and visible-pane state without duplicating paired tabs;
- projects you delete on the server disappear from every paired client's sidebar (no permanent ghost rows).

## Access and security

HiveWard creates a separate, revocable token for each paired client. The server lists these under **Shared Server Access**.

- Click the trash button beside a grant to revoke it. Active clients using that grant are disconnected immediately.
- Generating another link replaces the previous **unused** link. Clients that already paired keep their own grants until you revoke them.
- Keep Tailscale ACLs or grants as narrow as your setup allows.
- Do not forward the HiveWard port directly to the public internet. Prefer Tailscale, WireGuard, a trusted LAN, SSH forwarding, or an authenticated tunnel.
- Do not select `127.0.0.1` for another computer. That address only works on the server itself.

## Alternative: `hiveward serve`

Use `hiveward serve` when the host should run without the desktop window—for example, a headless Linux server or a service-managed VM. For a MacBook or desktop you can leave signed in, the in-app setup above is simpler.

Install HiveWard and its bundled CLI on the server, then run:

<Callout title="On Linux, start it with hiveward-ide serve">
  The Linux CLI is named `hiveward-ide`, because GNOME HiveWard's screen reader already owns
  `/usr/bin/hiveward`. A packaged `hiveward serve` does write a bare `hiveward` into `~/.local/bin`, but only
  while it is starting, so that shim can never be the command that starts the server. Read `hiveward
  serve` as `hiveward-ide serve` throughout this page when the host is Linux. See [Install →
  Linux](/docs/install#linux).
</Callout>

```bash
hiveward serve --pairing-address <server-tailscale-ip-or-hostname>
# Linux
hiveward-ide serve --pairing-address <server-tailscale-ip-or-hostname>
```

For example:

```bash
hiveward serve --pairing-address 100.64.1.20
# Linux
hiveward-ide serve --pairing-address 100.64.1.20
```

The command:

- starts the HiveWard runtime without opening the desktop window;
- on macOS, stays out of the Dock and the Cmd-Tab switcher until you open a desktop window from it;
- runs in the foreground until you press `Ctrl-C`;
- prints the bound endpoint and a runtime pairing URL;
- uses `--pairing-address` only for the address clients should dial.

Paste the printed pairing URL into **Settings → Remote HiveWard Servers → Add Server** on the client.

Add `--port 6768` when a firewall, tunnel, or service definition requires a fixed port:

```bash
hiveward serve --port 6768 --pairing-address 100.64.1.20
# Linux
hiveward-ide serve --port 6768 --pairing-address 100.64.1.20
```

Use only one host mode at a time. If the HiveWard desktop app is already sharing that computer, do not start a second `hiveward serve` process for the same setup.

`hiveward serve` runs on HiveWard's own Node server (hivewardd) by default. If hivewardd can't serve on this computer, it uses the desktop app's server instead and prints one line saying why. On a packaged macOS app it currently always uses the desktop app's server, so paired clients can still update it. To always use the desktop app's server, set `HIVEWARD_SERVE_RUNTIME=electron`.

### Limit terminal memory on a Linux server

By default, nothing caps how much memory a terminal's processes use, so one runaway job can push the whole server into the kernel's out-of-memory killer. On Linux you can cap each terminal by setting these variables in the environment that starts `hiveward serve` (or in its service unit):

```bash
export HIVEWARD_TERMINAL_MEMORY_MAX=16G      # memory per terminal, 256M or more
export HIVEWARD_TERMINAL_MEMORY_SWAP_MAX=0   # swap per terminal; 0 means no swap
hiveward-ide serve --pairing-address 100.64.1.20
```

- Each terminal already runs in its own systemd user scope. The limits become that scope's `MemoryMax` and `MemorySwapMax`.
- When a terminal goes over its limit, the kernel kills its largest process. Typically that is the job, and the shell keeps running. The server and every other terminal keep running.
- The limits are off by default because HiveWard can't know what a sensible limit is for your workloads.
- They need systemd with cgroup v2 and a user manager that outlives logout (`loginctl enable-linger <user>`). If the host can't enforce a limit, HiveWard skips it, logs `terminal-memory-limits` in the terminal host log, and starts terminals without it.
- HiveWard reads them only when its terminal host process starts. That process keeps running when `hiveward serve` restarts, so terminals keep their old limits until it restarts too, for example after the server reboots.
- They have no effect on macOS or Windows.

### Use the GPU on a Linux server

On Linux, `hiveward serve` turns off hardware acceleration by default, because most headless hosts have no GPU and a failing GPU process can stop the server from starting. Browser panes then render in software. If the host gives the HiveWard process a GPU (for example a render node such as `/dev/dri/renderD128`), set `HIVEWARD_SERVE_GPU=1` in the environment that starts `hiveward serve` (or in its service unit) to keep hardware acceleration on:

```bash
export HIVEWARD_SERVE_GPU=1
hiveward-ide serve --pairing-address 100.64.1.20
```

This only stops HiveWard from turning the GPU off. Chromium may still render in software on HiveWard's own Xvfb, which has no GPU of its own; open `chrome://gpu` in a browser pane to check, and point `DISPLAY` at a GPU-backed X server if it reports software rendering. If you installed the server with `hiveward serve service install`, add the variable to the service unit yourself. If the server stops starting or browser panes crash with it set, unset it to go back to software rendering.

### Mobile from a headless server

For the HiveWard mobile app, request a mobile-scoped QR code and link:

```bash
hiveward serve --pairing-address 100.64.1.20 --mobile-pairing
# Linux
hiveward-ide serve --pairing-address 100.64.1.20 --mobile-pairing
```

Keep the phone on the same tailnet, open HiveWard Mobile, choose **Pair**, and scan the terminal QR code or paste the printed link.

## Desktop app or `hiveward serve`?

|               | Desktop app on the server           | `hiveward serve`                                       |
| ------------- | ----------------------------------- | -------------------------------------------------- |
| Best for      | An old laptop, Mac mini, or desktop | A headless Linux box, VM, or managed service       |
| Setup         | Settings and buttons                | Terminal command and service configuration         |
| Server window | Open                                | None                                               |
| Access link   | **New Link → Generate Access Link** | Printed in the terminal                            |
| Lifetime      | While the desktop app is running    | While the foreground process or service is running |

## Remote HiveWard Server or SSH?

Use [SSH worktrees](/docs/ssh) when HiveWard on your laptop should own the runtime and use another machine only to run selected worktrees and terminals.

Use a Remote HiveWard Server when the other machine should own the full HiveWard runtime and preserve shared sessions for desktop, browser, mobile, or automation clients.

See [Ways to run HiveWard](/docs/ways-to-run) for the full comparison.

## Troubleshooting

### The Tailscale address is not listed

On the server, confirm Tailscale is connected, then click the refresh button beside **Connection address**. Both computers must be signed in to the same tailnet. A Tailscale IPv4 address usually starts with `100.`.

### The server is disconnected

Confirm the server computer is awake, HiveWard is still running, and Tailscale shows both devices online. Check your tailnet ACLs or grants if one device cannot reach the other.

Update HiveWard on both computers if the server row reports an incompatible protocol version.

### The access link was shared with the wrong person

On the server, open **Settings → Remote HiveWard Servers → Shared Server Access** and revoke that grant. Generate a new link for the intended client.

### The server cannot find an agent CLI

Install and authenticate that CLI on the server computer. Remote sessions use the server's `PATH`, home directory, and credentials—not the client's.

### `hiveward serve` advertises the wrong address

Stop the command and restart it with an address the client can reach:

```bash
hiveward serve --pairing-address <reachable-tailscale-ip-or-hostname>
```

Do not use a wildcard address or `127.0.0.1` for a remote client.
