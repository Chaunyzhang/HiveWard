### Homebrew (macOS)

HiveWard is also published as a Homebrew cask, auto-bumped on every stable release:

```
brew install --cask Chaunyzhang/HiveWard/hiveward
```

`brew upgrade --cask Chaunyzhang/HiveWard/hiveward` picks up new stable builds. Always use the full name: bare `hiveward` is an unrelated Plotly cask. The cask tracks the stable channel — for RC builds, use the GitHub Releases links above or the in-app **Check for Updates** flow described under [Updates](#updates).

## First launch

On first launch HiveWard will:

- Ask for access to your home directory so it can add repos.
- Offer to import `~/.claude`, `~/.codex`, and Ghostty terminal settings if present.
- Drop you on an empty landing screen where you add your first repo.

## Updates

HiveWard auto-updates by default, tracking the **stable** channel. Stable releases are vetted; **RC (release candidate)** builds ship new features first, often daily.

On Linux, whether HiveWard can apply an update itself depends on which package you installed. See [Linux](#linux) before you pick one.

There is no permanent in-app opt-in for the RC channel. Modifier clicks on **Check for Updates** ([Settings → General → Updates](/docs/settings), or the app / Help menu):

| Modifier                                               | Effect                                                                         |
| ------------------------------------------------------ | ------------------------------------------------------------------------------ |
| **Shift+click**                                        | Include the latest **RC** prerelease                                           |
| **Cmd+click** (macOS) / **Ctrl+click** (Windows/Linux) | Latest **perf**-tagged prerelease                                              |
| **Option+click** (macOS only)                          | Pick a **validated local macOS build** that passes HiveWard’s compatibility checks |

You can still download any build directly from the [GitHub Releases page](https://github.com/Chaunyzhang/HiveWard/releases).

<Callout title="Don't like the current update">
  Older versions are always available on the [GitHub Releases

  if you go back.
</Callout>

## Platform notes

### macOS

Signed and notarized. On first launch, macOS may still ask you to confirm — that's normal for Electron-based apps.

### Windows

The default shell can be set to PowerShell or CMD under [Settings → Terminal](/docs/settings). Most users want PowerShell.

### Linux

Each published release ships three Linux packages — an **AppImage**, a **`.deb`**, and an **`.rpm`** — for both x64 and arm64. They contain the same app. What differs is how updates reach you, so pick on that.

| Package      | Pick it when                                              | Updates                                                           |
| ------------ | --------------------------------------------------------- | ----------------------------------------------------------------- |
| **AppImage** | You want HiveWard to update itself, like on macOS and Windows | HiveWard downloads and applies the update in place                    |
| **`.deb`**   | You manage software with `apt` on Debian or Ubuntu        | HiveWard tells you a version is out and hands you the install command |
| **`.rpm`**   | You manage software with `dnf`, `yum`, or `zypper`        | Same as `.deb`                                                    |

The AppImage has a stable download link per architecture — [`hiveward-linux.AppImage`](https://github.com/Chaunyzhang/HiveWard/releases/latest/download/hiveward-linux.AppImage) for x64 and [`hiveward-linux-arm64.AppImage`](https://github.com/Chaunyzhang/HiveWard/releases/latest/download/hiveward-linux-arm64.AppImage) for arm64 — and needs `chmod +x` before its first run, because GitHub release assets carry no permission bits. The `.deb` and `.rpm` filenames carry the version and architecture, and the two formats spell architecture differently (`hiveward-ide_<version>_amd64.deb` or `_arm64.deb`; `hiveward-ide-<version>.x86_64.rpm` or `.aarch64.rpm`), so take those from the [Releases page](https://github.com/Chaunyzhang/HiveWard/releases) rather than a fixed URL.

#### How updating works

**The AppImage self-updates.** Choose it if you want automatic updates. HiveWard checks for a new release, you click **Update**, and it replaces the AppImage in place — the same flow as macOS and Windows.

**The `.deb` and `.rpm` do not self-update.** HiveWard still notices the new version and downloads the package, then gives you a **Copy Install Command** button. Copy it rather than retyping it: HiveWard resolves every program to an absolute path in a trusted system directory and single-quotes the package path, so what you paste looks like this:

```
/usr/bin/sudo /usr/bin/apt -o Binary::file::APT::Sandbox::User=root install -- '/home/you/.cache/hiveward-updater/pending/hiveward-ide_1.4.194_amd64.deb'
```

Which package manager appears depends on what your system actually has: `apt`, else `dpkg -i`, for a `.deb`; `zypper`, `dnf`, `yum`, then `rpm -Uvh` for an `.rpm`. The download directory follows `XDG_CACHE_HOME` when that is set and falls back to `~/.cache` when it is not.

**Quit HiveWard before you run the command**, then reopen it once the install finishes. You are replacing the files of a running application, and the package manager cannot swap them safely underneath a live process. HiveWard deliberately never escalates privileges to do this for you: installing a system package needs root, `hiveward serve` runs as an unprivileged user, and a headless machine has no authentication agent to prompt. VS Code and Signal make the same call on `.deb`.

**A distro-managed build is left alone.** If you are running a repackaged HiveWard — an AUR build, a Nix derivation — HiveWard sees that no package manager it can drive owns this install and stops offering a download it could never apply. It still reports that a new version exists, so you can update the way you normally would.

#### The CLI command is `hiveward-ide`

On Linux the [HiveWard CLI](/docs/cli/reference) installs as **`hiveward-ide`**, not `hiveward`. GNOME HiveWard — the screen reader that ships by default on Ubuntu and other GNOME desktops — already owns `/usr/bin/hiveward`, and HiveWard will not shadow it. The `.deb` and `.rpm` packages are named `hiveward-ide` for the same reason.

- The `.deb` and `.rpm` put `hiveward-ide` on your `PATH` at install time, as `/usr/bin/hiveward-ide`.
- With the AppImage, register the CLI from [Settings → General → HiveWard CLI](/docs/settings). That installs `~/.local/bin/hiveward-ide`.
- Inside HiveWard's own terminals, bare `hiveward` works. HiveWard puts a shim on the `PATH` of the terminals it manages, so agents and scripts running there use the same command as on macOS and Windows.
- On a headless host, a packaged `hiveward serve` writes a bare `hiveward` into `~/.local/bin` as it starts, unless a file it does not own already holds that name. It writes that _during_ startup, so it is never what starts the server — the first launch is always [`hiveward-ide serve`](/docs/remote-servers).

Do not verify with `command -v hiveward`: on a GNOME desktop that succeeds and resolves to the screen reader. Use `hiveward-ide` in your own shell and `hiveward` inside HiveWard. If you want the short name everywhere and you do not use the screen reader, link it yourself:

```
ln -s "$(command -v hiveward-ide)" ~/.local/bin/hiveward
```
